## 3. 왜 stage3가 14턴으로 떨어졌나 — 가설

stage3 자가수정 1회만 발생 (run #4 대비 -67%). 직접 원인은 stage2 모델
변경이 아니다 (stage2 시나리오 품질·길이는 #4와 비슷). 가능 원인:

1. **stage1 prompt 보강(사전 검증 메모) + stage2 시나리오의 결합 효과**
   가 #4보다 stage3 작성 정확도를 더 높였다.
2. **시드 데이터·환경 안정성**: 같은 `/management/logs` 73건 시드를
   여러 라이브에서 반복 쓰면서 시나리오·spec 매칭이 안정.
3. **uncontrolled noise**: 단일 실행 데이터라 진짜 14턴이 평균인지,
   운 좋게 빨리 통과한 한 사례인지는 추가 실행 1~2회로 확인 필요.

→ **결론은 변하지 않음**: 어쨌든 비용·시간이 크게 줄었고 quality도
   유지됐다. stage3 추가 측정은 후속 라이브에서.
