# stage1 매핑 오분류 누적 기록

stage1 에이전트가 만든 매핑 표에서 **실제와 어긋난 분류**를 사용자가
교정해준 항목을 누적한다. 이 문서는 2주차 stage1 prompt 보강의 직접
입력이 된다 (어긋난 패턴 = 에이전트가 추가로 받아야 할 컨텍스트의 단서).

## WebSocket 의존 분류 — 사용자 확정 정정 (2026-05-05)

| 라우트 | 에이전트 분류 | 실제 | 비고 |
|---|---|---|---|
| `/monitoring/live/2d/all` | yes | **yes** | 정확 |
| `/monitoring/live/3d/t1` | yes | **yes** | 정확 |
| `/monitoring/live/3d/t2` | yes | **yes** | 정확 |
| `/monitoring/summary` | yes | **no** | ❌ 오분류 |
| `/dashboard/replay` | yes | **no** | ❌ 오분류 — DB 적재 좌표 재생 |

**진실 (사용자 확정):** WebSocket을 쓰는 라우트는 `/monitoring/live/*` 3개뿐.

## 에이전트가 헷갈린 신호 패턴

### `/dashboard/replay`
- **에이전트 추론**: "ws-positions 컨텍스트 공유 + 시간슬라이더 RX"
- **실제**: DB에 적재된 라이브 승객 좌표를 REST로 불러와 재생
- **혼동 원인**: live 뷰와 같은 캔버스/뷰어 컴포넌트를 재사용하는 것을
  "데이터 채널 공유"로 잘못 추론. **UI 컴포넌트 공유 ≠ 데이터 채널 공유**.

### `/monitoring/summary`
- **에이전트 추론**: 검색대 운영 라이브 카드 → 좌표 WS 위젯 백그라운드
  유지로 표시
- **실제**: WebSocket 미사용
- **혼동 원인**: `/monitoring/*` 트리에 진입한 페이지는 모두 WS를
  쓴다는 휴리스틱을 과적용한 것으로 추정.

## 2주차 stage1 prompt 보강 가이드

위 두 오류로부터 도출된 prompt 보강 항목:

1. **데이터 소스 직접 확인 강제**: 페이지에 WS 핸드셰이크가 일어나도,
   "그 핸드셰이크가 *이 페이지의 핵심 데이터*를 나르는가" 를 별도로
   확인. 다음 두 가지를 분리 기록:
   - 핸드셰이크 발생 (yes/no)
   - 핵심 데이터 페이로드가 WS 채널로 흐르는가 (yes/no)
2. **UI 컴포넌트 재사용 vs 데이터 채널 공유 구분**: 같은 캔버스/뷰어
   컴포넌트가 보이더라도, REST API 호출이 페이지의 핵심 데이터를
   가져온다면 WS 의존 아님.
3. **라우트 트리 휴리스틱 금지**: `/monitoring/*` 모두 WS, 같은 식의
   조상 라우트 기반 일괄 분류 금지. 각 페이지별로 직접 관찰.

## 트래킹 카운트
- 누적 오분류 (WebSocket): **2건** (총 5건 분류 중 40% 오류율)
- 영향: 1주차 stage2 후보에서 `/monitoring/summary`, `/dashboard/replay`
  가 자동 제외됨 — 후보 풀이 인위적으로 좁혀졌다.
